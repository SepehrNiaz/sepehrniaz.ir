Ports and protocols: TCP, UDP and the services behind them

What a port is, how TCP and UDP differ, the port numbers worth knowing by heart, and how to see which ports are open on a machine.

After this lesson you can
  • Explain what a port is and why a connection needs one
  • Choose between TCP and UDP for a given job
  • Name the common ports and check which are open

One address, many programs

An IP address brings data to a computer. But one computer runs many programs that use the network at the same time: a browser, a mail app, a game. How does the computer know which program an arriving packet is for? Each program is given a number between 0 and 65535, called a port. If the IP address is the address of a building, the port is the number of the flat. A connection is always described by both: 192.168.1.50:443 means 'port 443 on the machine 192.168.1.50'.

A program that waits for others to connect is called a server, and it listens on a fixed, well-known port so that everyone knows where to knock: web servers on 443, SSH on 22. The program that starts the conversation is the client; the operating system lends it a random high port (somewhere above 49152) just for that conversation. So a visit to a website might be a conversation between your port 51734 and the server's port 443.

TCP: careful and in order

TCP is like a phone call. Before any data is sent, the two sides agree to talk with three short messages — the three-way handshake. The client says SYN ('may I talk to you?'), the server answers SYN-ACK ('yes, and may I talk to you?'), and the client replies ACK ('yes'). After that, every piece of data is numbered and confirmed; anything that gets lost is sent again, and the pieces are put back in the right order. This makes TCP reliable, at the cost of a little speed. Web pages, email, file transfers and SSH all use it, because a missing piece would ruin them.

UDP: fast and without promises

UDP is like posting a card: you send it and hope. There is no handshake, no confirmation and no resending. That sounds worse, but it is exactly right when speed matters more than perfection, or when the question and answer are tiny. In a video call a lost fraction of a second is better skipped than delivered late. A DNS question fits in one packet, so a handshake would only waste time.

Ports 0 to 1023 are the 'well-known' ports, reserved for standard services; on Linux only the administrator may listen on them. 1024 to 49151 are registered for particular applications, and the rest are lent to clients.

Open, closed and filtered

When you knock on a port, one of three things happens. If a program is listening, it answers and the port is open. If nothing is listening, the machine itself answers 'nobody here' at once — the port is closed. If a firewall is in the way, your knock is silently thrown away and you wait until you give up — the port is filtered. This difference is a useful clue: an instant refusal means the machine is alive but the service is not running; a long silence means a firewall, or no machine at all.

Looking at ports yourself

To check many ports on many machines you use a port scanner. The Port Scanner in the Tools section is a small one written in Python — its build tutorial shows that scanning is nothing more than trying to open a TCP connection to each port and noting which ones answer. Scan only networks that are yours or that you have written permission to test.

Ports and security

  • Every open port is a door. The fewer doors, the less there is to defend.
  • The question is never only 'is it open?' but 'open to whom?'. A database port open to the web server is normal; open to the whole internet is an incident waiting to happen.
  • Moving a service to an unusual port (SSH on 2222) reduces noise from robots but is not protection; they scan all 65535.
  • Prefer the encrypted member of each pair: HTTPS over HTTP, SSH over Telnet, SFTP over FTP, IMAPS over IMAP.
  • A firewall rule has four parts — source, destination, port and action. Learn to read a rule aloud: 'allow TCP from the office network to the server on port 443'.

Common mistakes

  • Opening a port on the router 'just to test' and forgetting it.
  • Confusing closed (instant refusal) with filtered (silence).
  • Testing a UDP service with a TCP tool and concluding it is down.
  • Believing a changed port number hides a service.

Exercises

Try each one yourself first, then open the answer.

  1. Which transport protocol and port does a normal DNS question use, and why?

    Show the answer
    UDP port 53. The question and answer each fit in one packet, so a handshake would only add delay.

  2. Put the three messages of the TCP handshake in order.

    Show the answer
    SYN → SYN-ACK → ACK

  3. A scan of a switch shows port 23 open. What is it, and what do you do?

    Show the answer
    Telnet — an unencrypted terminal. Turn it off and manage the switch over SSH (port 22) instead.

  4. nc to a server's port 443 fails at once with 'connection refused'. What does that tell you?

    Show the answer
    The machine is reachable, but no program is listening on 443: the web server is stopped or listening elsewhere. It is not a firewall — a firewall would give silence.

Practise this in the lab

Remember
  • IP address = the machine; port = the program.
  • TCP: handshake, reliable, ordered. UDP: no promises, fast.
  • 22 SSH, 53 DNS, 80/443 web, 3389 RDP.
  • Open, closed and filtered give three different answers.
