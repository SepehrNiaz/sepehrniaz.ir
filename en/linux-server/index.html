Running a Linux server

The daily work of an administrator: connecting with SSH, installing and updating software, starting services, reading logs, the firewall and backups.

After this lesson you can
  • Log in to a server with SSH and a key pair
  • Install software and control services with apt and systemctl
  • Find the cause of a problem in the logs
  • Protect a new server in its first hour

What makes a computer a server?

A server is not a special kind of machine. It is any computer whose job is to answer requests from other computers: to hand out web pages, store files, keep a database or record camera footage. It usually has no screen or keyboard, runs day and night, and is managed from somewhere else through a terminal. So everything you learned on the path so far — moving around, files, permissions, text tools — is exactly what you use here. This lesson adds the five things that are new: remote access, software, services, logs and protection.

Connecting from far away: SSH

SSH (secure shell) opens a terminal on another machine over an encrypted connection. You give a user name and the server's address; after you log in, every command you type runs there, not on your own computer.

Passwords can be guessed, so professionals log in with a key pair instead. You create two files: a private key that never leaves your computer, and a public key that you place on the server. The server lets in whoever proves they hold the private key.

Software: the package manager

On Linux you do not download installers from websites. The system has a catalogue of tested software called a repository, and a package manager that installs from it and keeps everything up to date. On Ubuntu and Debian the tool is apt; on Red Hat, Rocky and Fedora it is dnf, with the same ideas.

CommandWhat it does
sudo apt updateRefresh the catalogue (installs nothing)
sudo apt upgradeInstall the waiting updates
sudo apt install nginxInstall a program
sudo apt remove nginxRemove it
apt search keywordLook for a program
apt show nginxRead about it before installing

Services: programs that run in the background

A web server or a database does not run in your terminal; it runs in the background as a service, started and watched by a system called systemd. You control services with one command, systemctl. The two ideas to keep apart are start (run it now) and enable (run it automatically after every restart). A service that was started but not enabled will be gone after the next reboot — a classic cause of 'it worked yesterday'.

Logs: finding out what happened

When a service will not start, do not guess — it has already written down why. Modern systems collect all logs in the journal, read with journalctl; many programs also write plain files under /var/log, which you read with the text tools of the previous lesson.

Who is listening? Ports

Each service waits for requests on a numbered port. Listing the listening ports shows what your server offers to the network — and anything in the list that you do not recognise deserves a question.

The firewall

A firewall decides which of those ports the outside world may reach. On Ubuntu the simple front end is ufw. The safe order matters: allow SSH first, then switch the firewall on — the other way round, you lock yourself out of your own server.

The first hour on a new server

  • Update everything: sudo apt update && sudo apt upgrade.
  • Create your own user and add it to the sudo group; stop using root directly.
  • Install your SSH key, check that it works, then turn off password login and root login in /etc/ssh/sshd_config (PasswordAuthentication no, PermitRootLogin no) and restart ssh.
  • Turn on the firewall, allowing only what you need.
  • Set the correct time zone: sudo timedatectl set-timezone Asia/Tehran — logs with the wrong time are useless.
  • Turn on automatic security updates: sudo apt install unattended-upgrades.
  • Set up a backup before you put anything valuable on the machine.

Common mistakes

  • Enabling the firewall before allowing SSH.
  • Starting a service but forgetting to enable it.
  • Turning off password login before checking that the key works — keep one session open while you test in another.
  • Working as root all day.
  • Having backups on the same disk as the data.

Exercises

Try each one yourself first, then open the answer.

  1. You installed nginx and it works, but after a reboot the website is down. What happened and what is the fix?

    Show the answer
    The service was started but not enabled.
sudo systemctl enable --now nginx

  2. Show the last 30 log lines of the ssh service.

    Show the answer
    journalctl -u ssh -n 30

  3. Allow web traffic (80 and 443) through ufw and check the result.

    Show the answer
    sudo ufw allow 80/tcp
sudo ufw allow 443/tcp
sudo ufw status

  4. Copy the folder /etc/nginx from the server 192.168.1.50 to your own machine as user sara.

    Show the answer
    scp -r sara@192.168.1.50:/etc/nginx .

Practise this in the lab

Remember
  • SSH with keys is the door; guard it.
  • apt installs, systemctl runs, journalctl explains.
  • start is for now, enable is for every boot.
  • Allow SSH, then enable the firewall.
  • Update, back up, and test the restore.
