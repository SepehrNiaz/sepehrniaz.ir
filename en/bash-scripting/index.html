Automate with Bash scripts

Turn a sequence of commands you type every day into one script you run with a single word.

After this lesson you can
  • Write a script, make it runnable and run it
  • Use variables, command output and if in a script
  • Repeat a task for many items with a loop

A Bash script is just a text file full of the same commands you'd type by hand, run top to bottom. If you do something more than twice, it's worth scripting. Create a file ending in .sh and start it with a special first line.

Your first script

The first line, called the shebang, tells the system which program should run the file. Then you add commands and comments (lines starting with #).

Run it

Make the file executable once with chmod, then run it. $(…) runs a command and drops its output into your line — here, today's date.

Variables and conditions

Always put variables in double quotes ("$host", not $host). It saves you from strange bugs when a value contains a space.

When is a script worth writing?

A simple rule: the third time you type the same group of commands, put them in a file. A script does the job the same way every time, at three in the morning, without forgetting a step. Typical first scripts are backups, clean-ups, health checks and installing the same software on several machines. For heavy text processing or anything longer than about a hundred lines, Python is usually the better tool.

Arguments and questions

A script becomes reusable when it takes its values from outside. The words typed after the script's name arrive as $1, $2 and so on; $# is how many there are, $@ is all of them, and $0 is the script's own name. read asks the person a question while the script runs.

Tests: asking yes-or-no questions

The square brackets are a command that answers yes or no. They need a space after [ and before ], and they have their own words for comparing.

TestTrue when
[ -f file ]the file exists
[ -d dir ]the folder exists
[ -s file ]the file exists and is not empty
[ -z "$a" ]the text is empty
[ "$a" = "$b" ]two texts are the same
[ "$n" -eq 5 ]numbers are equal (-ne not equal)
[ "$n" -gt 5 ]greater than (-ge at least, -lt less than, -le at most)
[ ! -f file ]! turns any test around

Exit codes: how commands report success

Every command ends with a number that you do not normally see. Zero means it worked; anything else means it did not. The special variable $? holds the code of the last command: after ls notes it is 0, and after ls nofile it is 2. if does not look at what a command printed — it looks at this number. Your own scripts should follow the same rule: exit 0 when all went well and exit 1 (or another number) when something failed, so other scripts and schedulers can tell.

Loops over files and over lines

Scripts that fail safely

By default Bash carries on after an error, which can be dangerous: if cd fails, the next rm runs in the wrong folder. Three settings at the top of a script change that.

Running a script on a schedule: cron

cron runs commands at fixed times. Type crontab -e and add one line per job. The line starts with five fields — minute, hour, day of the month, month, day of the week — and a star means 'every'.

A complete script: warn me before the disk fills

A checklist for every script

  • First line #!/bin/bash, second line a comment that says what the script does.
  • set -euo pipefail near the top.
  • Every variable in double quotes.
  • Check the arguments and print a usage line when they are missing.
  • Test with harmless values first — echo the rm command before you let it run.
  • Log what was done, with the date.
  • Never write a password inside a script; read it from a protected file (chmod 600).

Loops, arguments and exit codes

Every command finishes with an exit code: 0 means success, anything else means failure. That is what if really tests. Scripts also receive the words typed after their name: $1 is the first, $2 the second, and $# is how many there were.

  • No spaces around = when you set a variable: name="lab", not name = "lab".
  • $(command) puts a command's output into a variable.
  • Start serious scripts with set -e so they stop at the first error.
  • bash -x script.sh prints every line as it runs — the easiest way to find a bug.
  • To run a script every night, add a line with crontab -e .

Common mistakes

  • Spaces around the = sign.
  • Leaving out the spaces inside [ ] — it must be [ "$a" = "$b" ].
  • Forgetting the quotes around variables, which breaks on names with spaces.

Exercises

Try each one yourself first, then open the answer.

  1. What must the first line of a Bash script be?

    Show the answer
    #!/bin/bash

  2. Store today's date (YYYY-MM-DD) in a variable called today.

    Show the answer
    today=$(date +%Y-%m-%d)

  3. Write a loop that prints the name of every .log file in this folder.

    Show the answer
    for f in *.log; do
  echo "$f"
done

  4. Your script says 'Permission denied' when you run ./backup.sh. Why?

    Show the answer
    It is not executable yet: chmod +x backup.sh

Practise this in the lab

Remember
  • A script is the commands you already know, saved in a file.
  • Exit code 0 means success; if tests exactly that.
  • Quote your variables, and test with bash -x.
