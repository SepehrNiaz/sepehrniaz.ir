A real project: build a tool from start to finish

How a programmer turns a problem into a finished tool: describing it, cutting it into small functions, testing each one, handling mistakes and adding a command line.

After this lesson you can
  • Describe a tool in one paragraph before writing code
  • Cut a problem into small functions and test each as you go
  • Handle wrong input, add command-line options and write a first test

From exercises to a real program

Exercises teach you the words of a language. A project teaches you how to think: where to begin when the page is empty, how to keep a growing program under control, and how to know it works. The method below is the one behind all six tools in the Tools section. We will use it to build a small but genuinely useful one — a script that checks which devices on a list are reachable — and you can then repeat it for any idea of your own.

Step 1 — Write the problem in one paragraph

Before any code, write what the tool does in plain words, including what goes in and what comes out. If you cannot write that paragraph, you are not ready to write the program.

"The tool reads a text file with one device per line (name and address). It tries to connect to each device on a given port. It prints one line per device — UP with the response time, or DOWN — and a summary at the end. It exits with code 1 if anything is down, so that other scripts can react."

Step 2 — Cut it into small jobs

Read the paragraph again and underline the verbs: reads, tries to connect, prints, summarises. Each verb becomes a function with one clear job, clear inputs and a clear result. A good function fits on one screen and can be explained in one sentence.

FunctionTakesGives back
load_devices(path)a file namea list of (name, address) pairs
check(address, port)an address and a portthe response time, or None if down
report(results)the list of resultsprints the table and returns how many are down
main()the command-line argumentscalls the others in order

Step 3 — Build one function, and try it at once

Never write the whole program and then run it for the first time: you will get twenty errors and no idea where to start. Write one function, call it with a simple value, look at the result, and only then go on.

Step 5 — Expect things to go wrong

A program that works with perfect input is half finished. Ask of every input: what if it is missing, empty or wrong? Then decide what the program should say. A good error message names the problem and tells the person what to do next.

What if …The tool should
the file does not exist?say "devices.txt not found" and exit with code 2
a line has three words, or one?name the line number and skip it
the list is empty?say so, instead of printing '0 up, 0 down'
a device takes a minute to refuse?give up after the timeout

Step 6 — A proper command line

The file name and the port are written inside the program, so changing them means editing the code. The argparse module turns them into options, checks them, and writes the --help text for you.

Step 7 — Tests that check your work for you

Each time you change the program, something that used to work may break. A test is a tiny program that calls one of your functions and compares the answer with the one you expect. Once written, a hundred tests run in a second, every time, and never get bored.

Step 8 — Make it usable by someone else

  • A README of ten lines: what it does, how to run it, one example with its output.
  • Names that explain themselves, and a docstring on every function.
  • No passwords, addresses of real customers or personal paths in the code.
  • Keep versions with git, even when you work alone: git init, then git commit after every step that works. It is an undo button for the whole project.
  • Then improve it in small steps: check the devices in parallel, write the result as HTML, send a message when something goes down. That is how the Network Uptime Monitor in the Tools section grew out of exactly this script.

Ideas for your own first project

  • Rename the photos in a folder by the date they were taken.
  • Read a CSV of expenses and print the total for each month.
  • Check a list of websites every hour and note which ones are slow.
  • Count the words in a book and show the twenty most common.
  • Turn a list of names and extensions into a printable phone directory in HTML.
  • Pick the one closest to a problem you actually have. A tool you use is a tool you will finish.

Common mistakes

  • Writing two hundred lines before running anything.
  • One giant function that reads, calculates and prints.
  • Testing only with perfect input.
  • Values such as file names buried in the code.
  • No copy of the version that worked yesterday.

Exercises

Try each one yourself first, then open the answer.

  1. Write the one-paragraph description of a tool that counts how many times each word appears in a text file.

    Show the answer
    "The tool takes the name of a text file. It reads the file, turns everything to small letters, splits it into words and counts each word. It prints the twenty most frequent words with their counts, most frequent first. If the file does not exist it says so and exits with code 2."

  2. Which functions would you cut that tool into?

    Show the answer
    read_text(path) → text; count_words(text) → dictionary of counts; top(counts, n) → the n largest; main() → reads the arguments and prints.

  3. load_devices crashes with 'ValueError: not enough values to unpack' on a line that contains only a name. Make it skip such lines with a warning.

    Show the answer
    parts = line.split()
if len(parts) != 2:
    print("skipping line:", line)
    continue
name, address = parts

  4. What do the lines if __name__ == "__main__": main() do?

    Show the answer
    They run main() only when the file is started directly, not when another file imports it — so tests can import the functions without running the tool.

Remember
  • Describe, divide, build one piece, try it, repeat.
  • One function, one job.
  • Plan for missing and wrong input.
  • Tests and git let you change code without fear.
