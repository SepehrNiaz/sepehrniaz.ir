Network troubleshooting: a method that always works

Stop guessing. A fixed order of tests, the tools for each one on Windows and Linux, and seven real faults with their causes.

After this lesson you can
  • Ask the three questions that narrow a fault down
  • Test in a fixed order and stop at the first failure
  • Read ping and traceroute output and recognise common faults

Why a method beats experience

When a user says 'the internet doesn't work', there are dozens of possible causes, from a loose cable to a fault at the provider. The beginner tries things at random: restarts the router, changes the DNS, reinstalls the driver. Sometimes it works, and nothing is learned. The professional asks a few questions, then tests in a fixed order from the nearest thing to the farthest. Each test cuts the remaining possibilities in half, and the first test that fails points at the fault. You do not need to be clever; you need to be orderly.

First, three questions

  • What exactly does not work? 'No website opens' and 'one website is slow' are different faults.
  • Who is affected? One device means the problem is in that device or its cable. A whole room points to a switch. Everyone points to the router or the provider.
  • What changed? A new device, an update, a moved cable. Most faults begin with a change.

The ladder: seven tests from near to far

#QuestionWindowsLinux
1Is the link up? (lights, Wi-Fi bars)ipconfig /allip link
2Do I have an address?ipconfigip addr
3Does my own network stack work?ping 127.0.0.1ping -c 3 127.0.0.1
4Can I reach the gateway?ping 192.168.1.1ping -c 3 192.168.1.1
5Can I reach the internet by address?ping 8.8.8.8ping -c 3 8.8.8.8
6Do names work?nslookup google.comdig google.com +short
7Does the service itself answer?Test-NetConnection host -Port 443nc -vz host 443

Stop at the first step that fails; everything before it is proven to work, and everything after it cannot be judged yet.

What each failure means

Fails atLook here
1Cable, wall socket, switch port, Wi-Fi password, a disabled adapter. Try another cable and another port.
2An address starting with 169.254 means DHCP did not answer: DHCP server down, pool empty, or the port is in the wrong VLAN.
3Rare: the network software of the computer is damaged. Reset it or reinstall the driver.
4Wrong address, mask or gateway; an address conflict; a faulty switch; the router is off.
5The local network is fine. The fault is the router's internet side or the provider. Check the router's WAN light and status page.
6DNS. Try another DNS server; clear the cache with ipconfig /flushdns.
7The network is fine; the service is down, or a firewall blocks that port.

Reading ping properly

  • time: under 5 ms inside a building, 20–80 ms to a server in the same region. Large jumps mean a busy or poor link.
  • packet loss: anything above 1% on a cable is a fault — usually a bad cable, a damaged port or interference on Wi-Fi.
  • 'Request timed out' — nothing came back: the target is off, or a firewall drops ping.
  • 'Destination host unreachable' — your own computer or a router says it has no way to get there: check the address and gateway.
  • A device that does not answer ping is not always down; many firewalls block ping. Test the real port instead.

Where does the path stop? traceroute

traceroute (tracert on Windows) lists every router between you and the destination. If the list stops at your own router, the problem is local. If it stops inside the provider's network, call them and read out the last address that answered. Stars in the middle of a list that later continues are normal — some routers simply do not reply.

Habits of a good troubleshooter

  • Change one thing at a time, and undo it if it did not help.
  • Write down what you tested and what you saw. Your notes are the report, and the answer to 'what did you do?'.
  • Keep a simple map of the network: which switch feeds which room, which address belongs to what.
  • Know what normal looks like — the usual ping time, the usual load — so that abnormal stands out.
  • After the fix, ask why it happened and what would stop it happening again.
  • The Network Uptime Monitor in the Tools section runs steps 4 and 7 of the ladder for every device, all day, so that you hear about a fault before the users do.

Common mistakes

  • Restarting everything before looking — the evidence disappears.
  • Changing several settings at once.
  • Assuming 'no ping reply' means 'device is off'.
  • Fixing the symptom and never finding the cause.

Exercises

Try each one yourself first, then open the answer.

  1. A laptop shows the address 169.254.17.3. Which step of the ladder failed and what do you check?

    Show the answer
    Step 2: DHCP did not answer. Check the cable or Wi-Fi, then whether the DHCP server is running and has free addresses.

  2. ping 192.168.1.1 works; ping 8.8.8.8 does not. Where is the fault?

    Show the answer
    Beyond the gateway: the router's internet connection or the provider. The local network is fine.

  3. Only one user in a room of ten has no network. Name the three most likely places to look.

    Show the answer
    That user's cable, the wall socket or switch port it uses, and the network settings of that computer.

  4. Ping to a server shows 12% packet loss on a cabled link. Is that acceptable?

    Show the answer
    No. A healthy cable shows 0%. Replace the cable and test another switch port.

Practise this in the lab

Remember
  • Ask: what, who, what changed.
  • Link → address → self → gateway → internet → names → service.
  • The first failing test points at the fault.
  • One change at a time, and write it down.
